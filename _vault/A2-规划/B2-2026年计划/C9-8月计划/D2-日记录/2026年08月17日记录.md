修复1,3,4的问题
**结论**

当前最需要优化的不是页面性能，而是 PLC 通信一致性、切换流程并发控制、权限校验和日志可靠性。这几项会直接影响现场操作安全。

**主要问题**

1. **[P0] 等待切换轮询可能重复执行**

原实现按固定间隔启动异步轮询，却没有判断上一轮是否完成；而单轮操作包含连接、写入、等待、整组读取和重试，耗时可能超过轮询间隔。下一轮因此可能与上一轮同时操作同一 PLC，造成重复写入、重复告警或重复复位。

建议改成“上一轮完成后再延迟”的串行调度，并增加设备级操作锁和切换批次标识。

2. **[P0] 参数覆盖权限实际上可以绕过**

授权密码 `***` 和身份判断都在界面层，主进程又直接信任界面传入的覆盖授权标记；生产环境仍可打开调试工具。

因此任何能操作客户端的人都可以绕过界面直接调用 IPC。最终权限必须由后端根据工号、登录凭证和岗位校验；客户端密码只能作为交互提示，不能作为安全凭证。

3. **[P1] 正式业务和测试页使用两套 PLC 编解码**

正式业务、测试模块和测试页面分别维护了不同的 Modbus 解析或地址转换实现。

这正是“测试页正常、正式切换异常”的主要来源。最近 FX5U 字序修复也需要修改多处。

建议正式业务统一调用 `plc-comm` 的 Adapter、地址解析和编解码，不再维护独立版本。

4. **[P1] 数据类型归一化存在数值错误风险**

原实现主要根据位宽强制归一化数据类型。这样：

- `32位 + float` 会错误变成 `int32`
- `32位 + uint32` 会错误变成 `int32`
- `16位 + uint16` 会错误变成 `int16`

正式业务与测试模块支持的数据类型分支也不一致。

应保留兼容的数据类型，仅在类型缺失时根据位数推断。

5. **[P1] 系统日志上传目前是假上传**

上传流程仍调用模拟实现，却会记录“上传成功”；手动上传查找的文件名与实际日志名称也不一致。

结果是界面可能显示上传成功，但文件没有真正上传。建议真实接口完成前明确显示“仅本地保存”，不要返回成功。

6. **[P1] 业务日志存在丢失窗口**

业务流程先等待上传，完成后才保存本地日志，上传期间崩溃会造成记录丢失。续传结束时又可能用失败列表覆盖整个队列，使续传期间产生的新日志被遗漏。

建议采用 Outbox 模式：先持久化，再上传；续传按日志 ID 更新状态，不整表覆盖。

7. **[P1] PLC 核心逻辑没有自动化测试**

项目没有测试脚本，也没有发现测试文件。地址映射、字序和切换状态机都只能到现场验证，回归成本很高。

最应该先补表格驱动测试：覆盖典型设备地址的不同位宽读写、地址映射、字序、常用有符号/无符号/浮点类型、轮询期间禁止重复切换，以及离线日志续传不丢记录。

8. **[P2] 单文件职责过重**

核心业务文件同时承担 API、PLC 协议、配方、切换、日志、闭环、模拟和进程通信；界面状态模块也混合了配置、配方、卡片、日志和操作进度，职责明显过重。

建议在统一 PLC 通信后逐步拆成 `plc-core`、`recipe-service`、`changeover-service`、`log-outbox` 和 `client-ipc`，不建议一次性重写。

9. **[P2] 更新与环境配置需要收口**

更新源仍使用 HTTP，多个后端地址也散落在源码中。建议统一环境配置，并将更新源改为 HTTPS，正式安装包增加代码签名。

另外，当前项目的 `.git` 是空目录，`git status` 无法执行。开始较大重构前应先恢复或重新初始化 Git 仓库，否则无法可靠审查和回退。

1. 先解决轮询重入、服务端权限校验和假日志上传。

4. 改造日志 Outbox，再拆分超大模块。
